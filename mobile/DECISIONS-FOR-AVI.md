### Avi's decisions on the flagged forks (2026-07-22)
- **Build order → "Read-repository layer now":** every screen's reads route through a thin `lib/data/reads/` abstraction as features are built, so a future offline cache (PowerSync or persisted) swaps in cheaply — no per-screen refactor. Applied going forward + retrofitted to the existing office/financial read screens.
- **Financial writes → "Outbox + draft, flag RPC":** multi-step invoice/quote writes route through the durable outbox (ordered + retried), invoices start in `draft` until all line items land (safer than the web's client-side delete-reinsert, which has no retry). **FLAGGED TO JASON:** add an atomic Postgres RPC for invoice/quote writes as the true-transactional hardening.
- **Ship-gate reality (acknowledged):** "100% ship-ready in one go" is not achievable in-repo; GATE 1 (backend Bearer for send/PDF/Xero), GATE 2 (on-device human QA), GATE 3 (cross-system e2e), + store accounts (EAS) + PowerSync password (offline reads) are human/backend gates. Continuous build proceeds on all in-repo work; these gates are flagged, not claimed done.

### Gemini-2.5-pro adversarial findings (CRUCIAL — flagged to Avi)
1. **Build order — reorder recommended:** build the **offline-READ cache right after financial writes**, then build CRUD (Customers/Inventory/Fleet) *against the cache*. Building them online-first forces a costly refactor. (Counterpoint I raised: the offline-critical path is the field tech, already covered for writes; office users are usually online; the intended read-cache is PowerSync, which is BLOCKED on a DB-password step. So this is a real fork with cost either way.)
2. **Financial-write correctness (top 3 risks):** (a) `edit = delete-all-then-reinsert` is **non-transactional** — a partial failure corrupts an invoice (total but no items); needs a Postgres RPC transaction (the web app has this same client-side risk). (b) JS vs Postgres float math → UI total can mismatch the DB `GENERATED` line-total; treat DB as source of truth on refresh. (c) No optimistic-concurrency → two editors silently clobber; add a `version`/`updated_at` guard.
3. **Mobile porting:** don't clone the web "mega-form" — use a guided multi-step **wizard** (Select customer → Line items → Review).
4. **Honest "done" (independently confirms my caveat):** the app is **NOT shippable in-repo alone** — hard gates: **GATE 1** invoice/quote send/Xero (backend Bearer blocker), **GATE 2** on-device human QA (no simulator), **GATE 3** cross-system e2e (create on mobile → verify on web). Plus store accounts (EAS submit) + PowerSync password (offline reads).
